# Integration

How far the ported modules run together on the PC, per slice of `docs/ROADMAP.md`, and which stubs and provisional inputs the hosts use. Game rules stay in their subsystem docs; this page tracks wiring.

## Reachable from the hosts

Keep this list current: a ported module that no host calls is integration debt. Group by host; one line per module or chain.

- `MissionScene`: gameplay catalog, human/enemy/effect factories, dynamic subsets, MoveSystem, Collision, Emitter, Modifier and GarbageSystem Init/NeedsUpdate/Update (simulate profile), entity destruction/manager deletion, render frame/draw, SEB sprite evaluation, animation pass, BitmapMeshFrame/GL.
- `saga_mission` and `queue_capture`: MissionProfile owns the same archive managers, saved inputs, factories and scene step. The capture frontend supplies the PNG decoder; an empty decoder keeps the host independent of SDL and pixel preparation.
- `MissionHumans`: actual Human Init/event23+29 subscriptions and full frame dispatcher, total-stat and saved-level projection, state/formation/animation kernels, stage Z limits, FPS attack/recovery intervals and seeded recovery/celebration RNG. Shoot, bullet factory/launch, contact effects, Projectile Init/Update and ordered impact receivers use the concrete owner. Explicit reward profiles bind Enemy Defeat, saved defeat counters, pending EXP/treasure drops and ordinary-enemy landing fragments; stage_notifications additionally binds main-character game-over and boss defeat notification. Retry handling and complete stage/result/return execution remain unbound.
- `MissionHumans` enemy adapters: actual Enemy Init/event23+29+30 subscriptions, contact/recoil and death retarget receivers; optional Enemy5 Update includes population/lottery/system factories/targeting, HP blink, state helpers, culling/activation and shared RNG/FPS. Stage death/boss notification uses the optional scenario below; complete Stage Update remains unbound.
- `MissionHumans` collection adapter: actual front/hero selection, live drop subset, Treasure lookup, shared-ID number/common effect factories, native pickup/interpolation/credit/Garbage and stage accumulator. Numeric glyphs/audio are explicit presentation stubs.
- Not reachable from any host yet (tested only): permanent result grants, stage start/update/recovery/return, quest camera, cell system, event catalog/conditions/execution/dispatch, SelectForm passes, text modules, culture/collation/execution-context modules (deferred dependency work).

### Selected movement pass (S1 A3)

The simulate row enables optional Stage collection prefix -> Human -> Enemy -> Projectile -> Move -> Collision -> Emitter -> Modifier -> Animation -> Render -> Garbage, a subset of the native ordering, without placeholder callbacks for the other systems. MissionScene initializes the live And(0,1) group through initialize_movement; advance_movement uses factory-index11's actual gate and move_subset. No game rule is duplicated. Creation-order positions and movement counts are printed by bounded runs. Real enemies retain the velocity calculated by create_enemy from parameter5 and their record/creation flags. The hero retains its factory's zero velocity.

The complete 26-system schedule is still blocking. Ordinary bullets execute event23 in Human/Enemy/Projectile order with actual impact visuals, targeted numeric damage and emitter-tagged entity destruction. Emitter15 binds trail particles and falling-enemy debris to the same resource/factory/lifetime owner. Enemy5 Init/frame is bound with explicit scenario inputs. The optional Collision12 pass binds global pair dispatch and area delivery. The optional Stage3 collection prefix binds pickup and stage accumulation; permanent grants and mission termination remain unbound. Entity destruction is bound as described below; component pool reuse remains separate. Cell migration/culling and full camera/visibility remain open. The selected scene uses its fixed visible group even when an entity leaves the viewport.

Local demonstration: `build/viewer/queue_capture.exe research/exports/mission-data-scene/movement.txt 600 220 --run-frames 12`. The profile is the animation scene with simulate 0; tick_ms remains an explicit diagnostic timing input. Human0 remains at (0,0,0); enemy2 moves from (150,0,0) to (150,0,11.5068016) after 12 binary32 integrations. A native capture emits six quads through five textures; movement-loop.json and movement-12.bmp remain local. No Android golden replay is claimed.

### Entity destruction and effect expiry (S1 A3)

MissionEntities owns the destroyed flag and stable opaque lifetime handles independently of native entity IDs (temporary entities may share native ID -1). Destroy delegates to destroy_quest_entity and delete_entity_from_manager: ascending live component removal -> disposal of component notifications -> optional registry removal -> destroyed flag store. Duplicate destruction returns; callbacks update the existing subsets before event disposal. Nodes/components remain allocated so captured references stay valid; recycling and full World.Destroy are unbound.

MissionScene initializes the live And(22) subset and uses GarbagePass with factory-index31's gate. Counting finishes before deferred ordered destruction. The frame's render commands survive expiry, matching Render21 before Garbage31. The effect row calls the existing visual-effect factory with resource20, uses the selected SEB's header-derived lifetime and adds no Garbage for a looping effect.

Local demonstration: `build/viewer/queue_capture.exe research/exports/mission-data-scene/effects.txt 600 220 --run-frames 120`. It loads 23_effect alongside the character/enemy/hat/weapon archives, creates clip101 at (250,0,0), and reports its entity destroyed while the two actors remain live. effects-loop.json stays local. Synthetic GPU tests check that the expiring frame is visible and the next frame has no effect pixels; Windows tests check subset/registry removal, idempotent destruction, temporary lifetime identity and remove_registration=false.

### Stage death and boss notifications (S1 A3/A4)

MissionHumans registers the actual stage_human_dead receiver on event30 before Enemy Init registers retargeting. Human landing sends the shared event; the Stage receiver applies the native main-character flag2 gate and calls stage_game_over before Enemy retarget runs. Sub-character death therefore needs no game-over scenario. Main-character death and boss notification require an explicit stage_notifications row: initial Stage state/frame/retried, quest flags/completed, held-key bitmap and initial retry answer. Missing inputs still fail at the reached game-over/notification service after the native prefix.

The game-over adapter implements the narrow StageGameOverHost used by StageUpdateHost; it does not supply fake crystal, collection, recovery or town-return methods. If retried is true, native game-over stores state5 for main death and resets frame0. Otherwise it publishes a cost100 retry dialog with kind98/reason1 and the supplied answer. Both routes stop BGM and construct/push defeat presentation in the original order. Forms retain identity/lifetime and share one ordered observation stream; display and BGM output are service stubs. The host never runs update_stage on the stub dialog, chooses an answer or spends currency. Selected actor passes continue; original form-manager pause/resume remains unbound.

Boss landing invokes notify_boss_defeat through BossStageView referencing the actual collection.boss_defeated and max_z_rate fields. These stores precede UI callbacks, including failures. The quest projection is read at the original point after key-up and form-stack capture, rather than copied at entry. The native completion flag2/completed-byte gate controls victory presentation. Key releases mutate the scenario's held-key bitmap in native order; selected scenes have no QuestForm movement controls, so the two nullable lookups return null through a service stub. A reached nonnull-control touch-release path remains an explicit error. No reward-box pickup, quest completion or reward grant is inferred from notification.

### Headless execution limits

The host requires an explicit scene, frame count, FPS, DEBUG, backend name and seed. Only the existing explicit-seed System.Random adaptation is available; unsupported backends and unknown flags fail. Human-enabled profiles consume FPS for attack intervals and recovery cadence, and the seeded RNG for recovery/celebration. DEBUG also reaches the numeric damage gate; effective Android values and remaining consumers are unresolved. Scene runtime rows must agree with CLI configuration. Headless execution runs fixed logic passes without sleeping or multiplying movement by delta time. No complete-state hash, gameplay input replay, quest-table selection or save snapshot is claimed.

The original-data effects profile produces the same actor positions and destroyed flags after 120 passes in the headless host and the GPU frontend: enemy2 ends at z115.068047, effect101 is destroyed, and the hero remains still. host-loop.json and effects-loop.json are local evidence. Synthetic host tests additionally use invalid PNG payloads to prove that headless execution performs no PNG decoding and check strict rows, required simulate configuration, duplicate options and deterministic repeated output. GPU tests continue through the same loader/step.
