# Combat

Combat is driven by ECS systems: `HumanSystem` (party targeting and attack interval), `EnemySystem` (enemy attack timing, `Damage`, `Defeat`) and the collision/projectile handlers that call `Damage`. The hit test, damage arithmetic up to the HP subtraction, the attribute-affinity tables, the two Easing factors and the defeat trigger are established from static ARM64 analysis. The port composes hit testing, damage arithmetic, parameter subtraction and the post-callback death predicate with an explicit RNG source and host interface. A seeded public System.Random backend is available. A resolved-record host now connects character/equipment/enemy parameters and event callbacks; ECS entity-to-record lookup and projectile/contact entry orchestration are ported; concrete effects, state services and playable combat remain open.

## Overview

- `BattleSystem.Update` (0x114236c) only iterates its subset's enumerator to completion (with dispose/exception handling); it does not run attacks or damage. Do not attach combat logic to it by name.
- `HumanSystem.SearchAndAttack` (0x1156074): active-button and MP gates, nearest eligible enemy in XYZ, then destroyed/dead/fleeing/decorative rejection. Success stores the target, zeros Speed and changes to attacking state 2. This chain, the human movement/frame/burst orchestration and actual Shoot/spell/projectile production are ported; production catalog/world/audio bindings remain required.
- Damage entry points: `EnemySystem.OnBulletHit` (0x114f4ac) and two branches of `EnemySystem.OnCollide` (0x114f604) call `EnemySystem.Damage(attacker, receiver, attack, attackAttribute)` (0x114fc44, 3924 bytes; argument names from metadata). `Damage` returns a death flag; callers decide whether to call `EnemySystem.Defeat` (0x1150b98).
- `Damage` sends event 15 (`World.Send`, generic instantiation 2565) with receiver and the final damage `D`; `StageSystem.OnDamage` is a confirmed subscriber (see [rewards.md](rewards.md#quest-record)).

Parameter lookup (used throughout `Damage`): for entity E and index k, if E has the human component use `MemberSystem.GetTotalParamValue(k)`; else if it has the enemy component use `EnemyData.GetParamValue(k, EnemyComponent+0x10)`; else 0. Human takes precedence when both are present. `GetTotalParamValue` sums, in order and in 32 bits, `MemberSystem.GetParamValue(k)` + weapon + shield + hat + cloth contributions for k. Nominal names of indices 0/1/2/6/7/8/9 are not yet tied to the parameter catalog (0 is very likely HP).

Equipment getters and attribute bonuses now have portable contracts. Human base stats still go through an explicit provider: `MemberSystem.GetParamValue(Entity,k)` resolves `Entity.get_human` then `HumanComponent.get_data`, uses the character's level at +0x40, and calls the character-record overload. The latter calls `CharaData.GetParamValue(k,level)` and, for `get_isMain`, asks `MagicShopData.GetDataIdForParamKey(k)`; a result other than -1 selects a shop record and adds its `GetAddValue` with int32 wrapping. The numeric growth/shop path is now ported; per-parameter maximum levels, character records and shop records remain explicit data providers.

## Behaviour

### Human frame, movement and target acquisition

HumanSystem.Init (0x1154f10, 508 bytes) uses its supplied World, requests And({14}), stores its map, then StageSystem/EnemySystem/MemberSystem, in that order. The stored fields are subset +0x20, map +0x28, loopCounter +0x38 and systems +0x40/+0x48/+0x50. Nullable lookup results are stored unchanged. Subscribe Human.OnProjectileImpact to event 23, then Human.OnCollide to event 29. It does not reset loopCounter, actor state or previous subscriptions. Failure preserves earlier stores/subscriptions; repeating Init appends receivers. The port's StageHumanStart base is a transition-host view used by existing stage/retry code, not a claim about the original memory layout.

HumanSystem.Update (0x1155114, 804 bytes) traverses the captured live human group without an alive/destroyed filter. Capture each required Human component before dispatching its state: 0 waiting, 1 walking, 2 attacking, 3 bounding, 6 celebration; 4/5 and unknown values do no state-helper work. After dispatch:

1. Increment the captured Human.attackFrame with int32 wrapping. If the entry state was 2, retain that count while the captured component still has state 2; otherwise, when the count exceeds the current attack interval, reset to zero. For other entry states, clamp excess to a second freshly queried interval; both queries and their ordering remain observable. The counter does not wrap modulo INT_MAX.
2. Limit current entity Position.z. Capture stored stage for GetZ(minZRate), then re-read stored stage for GetZ(maxZRate). Capture current Z, then another Position pointer. Ordered Z>binary32(wrap32(firstZ+108)) writes that upper limit; otherwise ordered current Z<binary32(lastZ) writes a freshly queried Position. Do not alter X/Y or velocity.
3. Only positive captured invincibleTime decrements; zero/negative values are retained, including INT_MIN. When the new value is zero and the current entity has a type-3 Modify component, run the actual detach/pool-return kernel. Other modifier types remain. Then increment captured Human.frame as wrap32(frame+1)%INT_MAX. Replacement of slot 14 does not redirect these captured stores.
4. After the whole group succeeds, increment HumanSystem.loopCounter with the same modulo rule. Entity failure, pool-return failure or structural cursor invalidation propagates and skips this final system increment; preceding actor writes remain.

StageSystem.get_isAttackActive (0x115651c) requires the captured button array and visits required buttons in order until state exactly 1. An empty array returns false; a later null button is never visited after a match. It does not check stage state, boss state, pause or HP. SearchAndAttack requires the stored stage before checking its actor argument, so an inactive stage can return false for a null actor. Otherwise:

- Resolve the actor's current Character record. Main flag 2 selects stored Stage.attackAttribute_ (+0x70); nonmain characters select Data.equipmentData[Character.weaponId_].attribute, independent of their currently equipped weapon ID.
- CheckMp captures current ParamSet[1], its wrap32(maximum+extraMaximum), then wrap32(value+extra). GetUseMp resolves the current equipped weapon and returns wrap32(base useMp+trunc(attributeBonus/4)). Attribute bonus is the stored MemberSystem's total parameter attribute+10 for attributes 0..2, otherwise zero. Allow `(cost>maximum && value>=maximum) || value>=cost`: a completely full MP pool can pass a cost above its maximum. No positive-cost or positive-maximum guard is added.
- Capture stored EnemySystem before capturing the actor's Position pointer and computing GetDistance. Distance uses the current equipped weapon's distance +0x70, plus trunc(attributeBonus/30), with an upper-only signed cap 12. BurstCount similarly uses current weapon.burstCount +0x74 plus trunc(bonus/20), upper cap 10; neither result has a lower clamp. Bonus selection re-resolves the current Character/attack attribute.
- Enemy.SearchNearestEnemy scans the captured enemy group in live slot order, requiring each entity/Enemy. Skip exactly state 4, then skip wrap32(HP.value+extra)<1. Compute binary32 XYZ squared distance in order (dx*dx+dy*dy)+dz*dz; Y matters here. The radius is binary32(wrap32(distance*28)), squared, with an inclusive range test and strict first-nearest comparison from FLT_MAX. Empty/no eligible groups need no nonnull origin Position. It does not filter destroyed, fleeing state 5 or NO_ANIMATION at this stage.
- After nearest selection, reject null/destroyed, dead state 4, fleeing state 5 or required EnemyData.NO_ANIMATION flag 1. Rejection preserves the actor's old target/velocity and does not retry a farther candidate. Success writes the current Human.opponent, zeros all three Speed components, then runs real ChangeState(2).

GetAttackSpeed is trunc(wrap32(P6+100)/2). GetAttackInterval queries live FPS before that stat and returns max(SDIV(wrap32(FPS*100),speed),2); GetBurstInterval uses FPS*10 instead. ARM SDIV divisor zero yields zero, followed by the floor 2. GetMoveSpeed uses trunc(wrap32(P5+100)/2), converts to binary32, multiplies by 2.23 and divides by 100 as separate operations. It has no enemy-style minimum and can be negative after a wrapped/negative stat. Member totals reuse the existing live ECS character/equipment/saved-level projection, now exposed for movement and recovery too.

UseMp (0x11571c4) is a separate operation from the affordability calculation: capture ParamSet[1] before looking up the current equipped weapon, then call Parameter.Sub using only weapon.useMp (+0x7c). The attribute addition in GetUseMp is not subtracted by this method. For example, synthetic base cost 3 and attribute bonus 120 produce a gate cost 33 but UseMp changes base MP 30 ->27. Shoot now invokes this kernel after its first affordability gate and before its second affordability query.

UpdateWaiting first tries SearchAndAttack. If that fails, only sub flag 4 computes Member.GetFormationX and GetFormationZ, requiring the stored member pointer separately for each call, then reads actor X/Z. An ordered positive squared formation distance changes to walking state 1; equal/NaN distance does not.

UpdateWalking captures the global hero and hero Speed.z through the stored MemberSystem. Only captured hero Z velocity exactly zero tries SearchAndAttack before doing any walking work. Choose walking animation group 8 when actor dashSpeed>0, otherwise 40, comparing current Seb.id with its low two direction bits cleared; ChangeAnimation(newGroup,false) preserves its frame. Then:

- Main characters compute their own GetMoveSpeed and multiply by public Math.Sign of their current Z velocity. Sub characters with a moving captured hero compute their own speed and multiply by a fresh hero velocity sign. A positive sign additionally stops the sub's Z velocity when its current Z exceeds the captured hero's current Z; this guard does not run for reverse movement.
- When that captured hero velocity is zero, a sub captures its X/Z before querying formation. If squared X/Z distance is within moveSpeed squared, write target X, freshly write target Z and ChangeState(0). Otherwise calculate the binary32 length and set only Speed.z=(deltaZ*step)/length; original Speed.x is retained, even though deltaX contributed to the length. Do not add lateral tracking that the original does not perform.
- After those branches, capture Speed before reading current Z velocity, current Human.dashSpeed and a fresh velocity sign. Write velocity+dash*sign. Ordered positive velocity is multiplied by binary32 0.7; negative/zero velocity is not. X/Y velocity survives. Math.Sign's NaN case throws after preceding writes.
- Capture FPS before looking up current weapon.attribute. Attribute 3 replaces the recovery period with max(trunc(FPS/2),1); others retain raw FPS. On ARM remainder(loopCounter,period)==0, read total parameter 4 and consume exactly one inclusive Rand(3,5). Recovery percent is clamp(wrap32(draw+trunc(P4/3)),1,20). Capture ParamSet[0] then [1] before requiring either result. Compute each gain as max(trunc(wrap32(totalMaximum*percent)/100),wrap32(trunc(P4/2)+1)), then Parameter.Add HP followed by MP. This can run even when velocity becomes zero, and can consume a draw when both pools are full. Parameter.Add wraps the base value addition, uses the same lower-first/base-maximum-only clamp as Sub, and returns the excess; extra maxima influence the gain, not that clamp.

MoveBase (0x1158ab8) defaults a nonnegative speed below binary32 0.1 through GetMoveSpeed; negative speed teleports X then freshly queried Z, returns true and preserves all velocity/Y fields. Otherwise, within the inclusive squared distance threshold, the same arrival writes happen. Farther points set Speed.x and then fresh Speed.z from separately rounded delta*step/length and return false, preserving Speed.y. The original positive-distance square-root cap is retained using standard sqrt; no general math library is reconstructed. NaN speed takes the velocity path and can write NaNs. Move (0x1158914) first defaults nonpositive speed, including negative input, then calls MoveBase; NaN bypasses its default. A negative explicitly requested Move therefore differs from MoveBase's negative teleport.

UpdateBounding damps Speed.z by binary32 0.8, clears fresh Human.dashSpeed and settles only at ordered abs(fresh Speed.z)<0.1. Settling requires Direction (unlike the enemy helper's optional Direction), unlocks it, zeros fresh Z velocity and ChangeState(0). Celebration/UpdateBanzai zeros Z velocity, queries the required current character-library SEB clip-0 frame period, and at ARM remainder(Human.frame,period)==0 captures Direction before consuming bounded Rand(4), then writes the captured direction. ChangeAnimation(0,false) always follows, leaving frame/Y/X velocity intact. Zero and negative periods retain ARM remainder behavior.

UpdateAttacking captures current Human and its target. Null/destroyed, state 4/5 or inactive attack buttons clear the captured target and ChangeState(0). Otherwise compute the interval and burst wait even before the first shot is due. On captured attackFrame>=interval and ARM remainder(wrap32(attackFrame-interval),wait)==0, call required Shoot(actor,capturedTarget). A true result resets the current Seb.frame to zero; a false result still proceeds to the MP/end-of-burst gate. Read current MP total; nonpositive MP uses count 0, otherwise re-read BurstCount and subtract one. At attackFrame>=wrap32(interval+count*wait), reset captured attackFrame, clear its target and ChangeState(0). While that gate has not been reached, retain state/target and let the outer frame increment its counter. Distance and NO_ANIMATION are not rechecked in this helper. Actual Shoot (0x1156638) now selects spell/projectile data and creates the attack through the concrete producer described below; the required host binding has no dummy success fallback.

### Human shots and bullet creation

`HumanSystem.Shoot` (0x1156638, 1836 bytes) rejects a null/destroyed target or a target whose Enemy state is 4. It does not repeat HP, fleeing, distance, button or decorative-record checks. Require the actor, capture its current equipped weapon (a nullable row), then resolve its character record. Main-character flag 2 chooses the first BulletData row whose attribute equals the current stored Stage.attackAttribute; nonmain actors use the captured weapon.bulletId. The predicate (0x115931c) requires its row before requiring the stored Stage, so a null catalog slot faults rather than being skipped; an empty main-character catalog returns null without reading Stage. Equipment bulletId -1 returns null without querying Data.bulletData; other IDs use a bounds-checked array lookup and may return a null row. A missing selection returns false before MP mutation.

### Attack timing

- Human: P = `GetTotalParamValue(6)`; speed = (P + 100) / 2 with 32-bit add and truncation toward zero (ADD/CSEL/ASR, also for negative sums); interval = `ClampMin(SDIV(FPS*100, speed), 2)` with 32-bit multiply. ARM SDIV zero yields zero before the floor; no software zero-divisor guard.
- Enemy: V = `Parameter.get_value` of `ParamSet[6]` (value_+0x14 plus extra +0x1c); interval = `ClampMin(SDIV(FPS, V), 1)`; attack moment iff `enemy+0x1c % interval == 0` (SDIV/MSUB) where enemy = `Entity.enemy`. Not the human formula (no +100, /2 or ×100). EnemyComponent+0x1c is frame: ChangeState resets it and EnemySystem.Update increments it after its state helper. A true timing result is not proven to always produce an attack.
- `MyConfig.FPS`: static field offset 0x50 (field 24199, type 4527, GOT 0x27312d8). Value and consumption rate not fixed; do not convert intervals to seconds assuming 50/60 FPS.

### Damage pipeline (`EnemySystem.Damage`)

1. **Hit test** (0x114fd10-0x114fe94): `base = attacker human ? 90 : 80`; `adj = Clamp(wrap32(atk.P7 - trunc(rcv.P9 / 2)), -60, 15)`; threshold = base + adj (human 30..105, other 20..95; no extra clamp at 100). `hit = Random.Hits(threshold)`. On miss: `World.CreateEffect`, return false (before any further parameter read).
2. Read receiver `ParamSet[0]` (kept for the Sub). Receiver defence/attribute: human -> P2 via GetTotalParamValue, attribute = weapon field +0x58, bonus B = `MemberSystem.GetAttributeValue`; enemy -> P2 via EnemyData, attribute = data +0x4c, B = 0; other -> P2 = 0, attribute 4, B = 0. Attacker P8 by the usual lookup.
3. **Arithmetic** (0x1150108-0x1150218), all intermediates 32-bit, each /100 is signed truncating (magic 0x51eb851f):
   ```text
   R = Random.Rand(95, 105)
   I = GetAttributesAffinity(attackAttribute, rcvAttribute)
   X = trunc(wrap32(R * attack) / 100) - trunc(rcv.P2 / 4)
   Y = trunc(wrap32(X * wrap32(B + 100)) / 100)
   D = trunc(wrap32(ATTRIBUTE_AFFINITY_RATE[I] * Y) / 100)
   C = Random.Hits(trunc(atk.P8 / 2))            # critical
   if C:                 D = D * 170 / 100
   elif attacker human:  D = D * Easing(10,100,50, attacker.Parameter[1].rate, 0) / 100
   if rcvAttribute == attackAttribute:
                         D = D * (100 - Easing(1,30,98, wrap32(B - 1), 0)) / 100
   floor: human receiver Rand(1,3); enemy receiver Rand(3-I, 6-2*I) if (unsigned)I < 3 else Rand(1,1)
   D = ClampMin(D, floor)                          # "other" receivers skip the floor
   ```
   Crit and the human non-crit factor are exclusive, not cumulative. Do not merge percentages or defer rounding.
4. **Subtraction**: if `MyConfig.DEBUG` (static +0x4) is true and the attacker is not human, `Parameter.Sub` is skipped; the rest of the function still runs. Otherwise `Parameter.Sub(ParamSet[0], D)`.
5. **Effects**: label parameters use static tables +0x450/+0x458/+0x460 with attribute/affinity branches. After the numeric effect at 0x115069c, recheck Enemy at 0x11506a0..0x11506ac. Enemy receivers remove an existing ModifyAnimation (0x11506c8, detach before pool return) and add type4/maxFrame8 (0x115070c), zero translations/angle/frame/anchor, unit scales, alpha255, destroy/loop false. The nonenemy branch jumps to 0x1150710, so the positional effect is unconditional: clip0/image1/loop false at fresh receiver (x,y+10,z), call 0x115078c. Event15 (receiver,D) follows at 0x11507b8 through World.Send. present_combat_damage in [projectile_launch.cpp](../../src/core/gameplay/projectile_launch.cpp) implements this stateful suffix; Modifier18 executes shake and expiry. Desktop labels remain a declared presentation stub, without suppressing modifier/effect mutations.
6. **Diagnostics and result**: after event 15, the code reads `MyConfig.DEBUG` (+0x4) and a second flag (+0x70); only when both are set does it format a seven-element diagnostic payload and call the logging route (0x11507bc-0x1150a54). This presentation path remains in the host boundary. At 0x1150a64: return `Parameter.get_value(ParamSet[0]) < 1` (includes extraValue_). Event-15 callbacks run **before** this test, so they can affect it. `Damage` does not return the damage amount and does not call `Defeat`.

### Parameter.Sub (0x1178dec)

Layout: `value_` +0x14, `maxValue_` +0x18, `extraValue_` +0x1c, `extraMaxValue_` +0x20.
```text
cand = wrap32(value_ - amount); new = cand
if maxValue_ != 0: new = cand < 0 ? 0 : (cand > maxValue_ ? maxValue_ : cand)   # lower test first
value_ = new; return wrap32(cand - new)
```
Max 0 disables the clamp (value may go negative). Overkill returns a negative excess. With a negative maximum the lower test still wins. Extras are untouched. Not `std::clamp`.

### Parameter rate, equipment and attribute bonuses

`Parameter.get_rate` (0x1178c84) first returns 0 if the **base** maximum (+0x18) is zero, even when extra maximum is nonzero. Otherwise numerator is `wrap32(wrap32(value + extraValue) * 100)`; denominator is `wrap32(maxValue + extraMaxValue)`. ARM64 signed division precedes clamp to [0,100]; zero denominator yields 0 and INT_MIN/-1 yields INT_MIN (thus clamps to 0). Neither double precision nor a combined rational expression is equivalent for overflowing inputs.

The three equipment getters take an int32 parameter index and return an int32. Each reads a jagged row's first two integers **before** interpolation, faults on missing/short rows or invalid index, ignores trailing row values, and calls zero-amplitude Easing with duration 99 and progress `wrap32(level-1)`. They have no state writes. Data layout, confirmed by metadata field offsets:

| Record | Level int32 | Parameter rows reference |
|---|---|---|
| EquipmentData (weapon/shield) | +0x28 `level_` | +0x88 `status_` |
| HatData | +0x60 `level_` | +0x50 `parameters_` |
| ClothData | +0x20 `level_` | +0x58 `parameters_` |

`MemberSystem.GetTotalParamValue(Entity,k)` calls the base provider, then resolves weapon, shield, hat and cloth separately in that order, querying parameter k on each. Missing equipment faults; there is no zero-contribution fallback. It then sums base and the four contributions with int32 wrapping. The current port preserves provider order and failure short-circuiting. The entity overload of `GetAttributeValue` uses an unsigned comparison: attributes 0,1,2 select total parameters 10,11,12; all other values (including negatives) return 0 without resolving anything. The second overload at 0x1158ed4 uses the same guard with the character-record total provider; that provider is not ported here.

`EnemyData.GetParamValue(k,level)` (0x116ea04) reads row k at +0x68, its first two endpoints, then static per-parameter maximum k at +0x8. It calls Easing with duration `wrap32(maximum-1)`, progress `wrap32(level-1)` and amplitude **-50**, so equipment's linear kernel cannot be reused for enemies. The initial maximum values are established below; the -50 curve is now ported through the shared easing kernel. `CharaData.GetParamValue` instead uses amplitude 0 and a different per-parameter maximum table; indices 0/1 above their maximum also have a second growth term toward level 1200. The extra endpoint is truncation toward zero of `binary64(lastEndpoint) * 0.086` (ELF constant 0x6274a8). Its duration is wrap32(1200-maximum), progress wrap32(level-maximum), start 0 and amplitude 0; the result is added with int32 wrapping. The extra term runs only for indices 0/1 and signed level > maximum. All endpoint reads precede the maximum-table lookup; invalid rows fault even at clamped levels. The 0.086 product is finite and within int32 range for every int32 endpoint.

`MagicShopData.GetDataIdForParamKey` (0x1172564) maps parameter keys 0..4 to ids 0..4 and keys 10..12 to ids 5..7; every other key returns -1. `GetAddValue` (0x11725c4) returns wrap32(upValue_ * buyCount), at offsets +0x30/+0x40, without clamping or writes. `MemberSystem.GetParamValue(CharaData,k,level)` first computes growth, then reads `isMain` (bit 1 of the flags byte at +0x1c). Only main characters and mapped keys resolve a shop record and add its value. Negative counts and overflow remain observable. The overload at 0x115dd68 uses the stored level (+0x40); the explicit-level overload at 0x115dd80 does not replace its argument with the stored level.

### Initial parameter maximum levels

`CharaData.PARAM_MAX_LEVELS` (static +0x18) and `EnemyData.PARAM_MAX_LEVELS` (static +0x8) are separate int32 arrays of length 13, initialized from the same metadata field. ### Attribute affinity

`AppData..cctor` (0x1117b30, region 0x1119ef8-0x111a078) builds two statics:
- `+0x440`: 5 rows of 2 ints (pairs, per attacker attribute 0..4; rows 3 and 4 are `[-1,-1]` sentinels).
- `+0x448` `ATTRIBUTE_AFFINITY_RATE`: 4 ints from `RuntimeHelpers.InitializeArray` (field 24324 of PrivateImplementationDetails, default_data offset 187880, SHA-256 a83b4f7b...7f339 matching the field name). Selector->rate: 0->90, 1->45, 2->20, 3->60.

`GetAttributesAffinity(att, rcv)`: row = pairs[att]; `row[0]==rcv` -> 0; `row[1]==rcv` -> 2; else any element == -1 -> 3; else 1. Receiver is compared, never used as an index; attacker <0 or >=5 is an out-of-range fault (no fallback). Resulting rates: attributes 0-2 form a cycle (90 strong / 20 weak / 45 neutral, also 45 vs 3/4); attackers 3 and 4 always 60 except receiver -1, which matches the sentinel first and returns selector 0 (rate 90). These are initial values; later mutation is not excluded. Element names are not assigned.

### Easing factors

`Graph.Easing(start, end, duration, progress, amplitude)` (0x1c5df9c): progress < 0 -> start; progress >= duration -> end; inside: ratio = (float)progress/duration, plus amplitude-scaled sine correction (`FastMath.Sin` -> double, `JMath.ToRadians` [double pi 0x626c28, /180 0x627428], libc `sin` via PLT 0x25fe590; float pi at 0x627830, divisor 314.1592712402344 at 0x6278ac), times (end-start), plus start, truncated to int and limited toward the start/end direction. Separate float32 multiply and add, no FMA. Both combat calls have amplitude 0, so the sine term contributes nothing; across their 148 interior points the result equals `start + progress*(end-start)/duration` (integer). The zero-amplitude numeric path is now shared with EnemyData.GetExp, including descending endpoints, wrapping differences and saturating float-to-int conversion; `wrap32(B-1)` makes INT32_MIN become INT32_MAX (upper limit, factor 70). IEEE-754 default rounding assumed; FPCR not captured.

### RNG consumption order

Per `Damage` call: `Hits(threshold)` [1 draw, always] -> on hit: `Rand(95,105)` -> `Hits(P8/2)` -> floor `Rand(...)` (human or enemy receiver; `Rand(1,1)` still draws). Order must be preserved. Defeat adds draws (see [rewards.md](rewards.md#defeat-sequence)).

### Contact collision orchestration

`EnemySystem.OnCollide` (0x114f604, 1600 bytes) selects the first Enemy entity, otherwise the second. Bullet slot 29 on either input delegates to `OnBulletHit`, preferring the first bullet. Without bullets, Damage slot 33 on either input selects the first such source. That route returns if there is no Enemy or its destroyed byte +0x2c is nonzero; otherwise it passes Damage.parent +0x18, value +0x10 and attribute +0x14 to Damage, calls Defeat on a true result, then continues the common reaction even after Defeat. Without a Damage component, a missing Enemy faults.

The common reaction re-resolves EnemyData, calls CutInAnimation with wrapping int32 `(enemySeb << 2) + 24` and `(enemySeb << 2) | 2`, locks Direction if present and creates effect `(0,2,0)` at `(x,y+10,z+12)`. It then selects the first Human, otherwise the second; no Human or human state 4/5 returns after this effect. EnemyData is resolved again. Data flags bit 0 selects FlyAway(enemy,-100,100,-100,-50,true), enemy state 4 and contact sound, bypassing damage and recoil.

Otherwise enemy P3 at the current EnemyComponent level is evaluated before reading human invincibleTime. Values greater than zero skip Damage but still recoil. Damage receives the enemy as attacker, human as receiver, P3 and the captured EnemyData attribute. A lethal result calls FlyAway(human,-100,100,50,100,false), ChangeAnimation(16,1), effect `(0,24,0)` at `(x,y+10,z)`, then human state 4. It does not call EnemySystem.Defeat for the human.

Recoil queries stage progress at the enemy's current z. Distance is binary32 3 when signed progress is greater than 79 or EnemyComponent flags bit 0 is set. Otherwise distance is 10, raised to 16 only when CharacterData flags bit 2 (isSub) is set and human z is strictly greater than the member hero's z. Equal/unordered comparisons retain 10. The current enemy z is reduced by distance, speed.z becomes negative distance, enemy state becomes 3, and contact sound is played last. Human invincibility and a nonlethal/missed Damage result do not bypass recoil. Data and component flag fields are distinct.

EnemySystem.ChangeState (0x114d934, 72 bytes) writes EnemyComponent.state +0x18 and then resets frame +0x1c, with a fresh getter for each store. Same-state calls reset the frame too. It performs no animation or transition guard.

### Projectile launch payload

ProjectileSystem.Fire (0x1157230, 480 bytes) accepts start/end binary32 triples, int32 speed, parent, animate/rotate flags and an int32 height percentage. It computes end minus start, separate binary32 squares and left-associated sum, then binary32 square root. Duration is truncation of distance / binary32(speed). Height is truncation of distance / 3, multiplied by height percentage with int32 wrapping, then signed division by 100. Each float-to-int conversion uses ARM FCVTZS saturation (NaN gives zero), except an explicit positive-infinity check returns INT_MIN. Zero speed is not clamped and zero duration is allowed.

It adds Projectile slot 27 with start/end +0x10/+0x1c, speed +0x28, maxHeight +0x2c, frame 0 at +0x30, duration +0x34 and parent +0x38. All fields are initialized before slot-add notifications. If rotate is true, it adds ModifyAnimation type 7 with maxFrame 0, loop true and the other defaults listed for FlyAway. It does not remove an existing ModifyAnimation on this route. Finally animate adds Animation(rate 1, backup -1); return value is duration. Callbacks and failures retain earlier component additions. Component pools remain host-owned; their standard collection implementation is not reconstructed.

### Per-frame projectile motion

ProjectileSystem.Update (0x1160018, 2992 bytes including exception cleanup) iterates its projectile subset before dispatching any completed entity. Init at 0x115febc builds the required slot array [27,0,1] and subscribes OnProjectileImpact to event 23. Per entity, Update normalizes end minus start in three dimensions; exact zero magnitude yields the zero vector, with no epsilon test. It captures speed/frame and computes half = maxFrame / 2 with signed truncation toward zero.

For frame <= half, height is float Graph.Easing(start.y, start.y + maxHeight, half, frame, +80). Otherwise it is Easing(start.y + maxHeight, end.y, half, wrap32(frame-half), -80). It writes this height to Position.y, evaluates the same branch at progress+1, and sets Speed to (normalized.x * speed, nextHeight - currentHeight, normalized.z * speed). Position.x/z are not integrated by this system. The float curve has negative-progress and progress>=duration endpoint guards, separate binary32 operations and endpoint clamping; its sine path uses the same degree/radian conversion order as the integer combat curve. The existing implementation is now exposed as easing_float and reused by the 31-pass drop collection loop; its arithmetic is not duplicated.

If ModifyAnimation exists, projected horizontal speed is vx-vz and projected vertical speed is (vx+vz)*0.5 - vy. FastMath.Atan2 calls public binary64 atan2(vertical,horizontal), converts to degrees and adds binary32 180 for negative vertical speed; Update independently adds another 180 under the same condition. The result is converted to int32 (positive infinity maps to INT_MIN) and wrapping 90 is added before storing angle +0x28. This double correction is preserved rather than replaced with a normalized-angle convenience function.

Update increments Projectile.frame with wrapping int32 arithmetic. Only when the previous frame >=1 and current y <= end.y does it finish; unordered height comparisons do not finish. It snaps all three coordinates to end, zeros all three speed fields, removes ModifyAnimation if present (notifications before pool return), and appends the entity to the completion list. After the entire subset pass, it sends World.Send<Entity>(23, entity), then removes Projectile without a presence guard; finally it clears the completion list. Event callbacks therefore see the Projectile still attached and all prior movement-pass changes. The generated remover first checks its getter and returns without pooling if the callback already removed Projectile. ### Collision geometry

CollisionSystem.CheckHit (0x114698c, 524 bytes) requires the first entity, returns false when it lacks Collision slot 32, then requires the second and returns false if it lacks Collision. These presence gates precede all Position reads: a missing first Collision returns false even with a null second entity. No destroyed, Cell, Human/Enemy, mask or visited test occurs here.

CollisionComponent has int32 radius +0x10 and offsetX/Y/Z +0x14/+0x18/+0x1c; visited +0x20 is outside this method. Each center is Position's binary32 coordinate plus the corresponding int32 offset converted to binary32. The distance is `(dx*dx + dy*dy) + dz*dz`, with separate binary32 operations. The right-hand side is the signed-int32 interpretation of the wrapping square of the wrapping radius sum, converted to binary32. Distance <= that limit means a hit, including exact tangency. There is no radius clamp or square root. Negative radii can therefore still produce a positive squared limit, while square overflow can produce a negative limit and reject even coincident centers. NaN comparisons return false. Preserve this arithmetic rather than substituting a generic sphere library with wider integer operations.

### Bullet impact areas

EnemySystem.CreateImpactEffect (0x114ec84, 2088 bytes) takes the bullet entity and its owner. It requires Bullet slot 29, captures its data record, requires the owner weapon through Equip slot 8, then requires the captured bullet record. It captures BulletData.attribute (+0x24) and EquipmentData.range (+0x78) before calling MemberSystem.GetAttributeValue(owner,attribute). Effective range is min(wrap32(weaponRange + trunc(attributeValue/25)),4); there is no lower clamp. EquipmentData.Load writes range from fixed token 17 (zero-based); the combat table projection now retains it.

The source x/z divided by binary32 24 become cell coordinates by truncation (ARM FCVTZS: NaN -> 0, finite overflow saturates, with an explicit positive-infinity -> INT_MIN override). CellUtil.GetRange always starts with the center, even for negative/zero range, and only visits neighbors for range >= 2. Visit4Cells traverses initialized directions up (0,-1), right (1,0), down (0,1), left (-1,0), depth-first, with depth range-1. It adds an absolute cell and its relative offset only if no previously added cell has the same coordinates, but recurses even when the cell was already present. Coordinates and offset subtraction wrap as int32. Ranges 1..4 produce 1,5,13,25 unique cells, in discovery order, not row or breadth-first order. The list is fully built before any effect callback. The port implements this bounded impact use with a fixed 25-entry array, using standard C++ storage rather than reconstructing List/Find/delegate internals.

For each cell, the method reads the current source position and creates effect (101,capturedRecord.effectImg,0) at (sourceX + binary32(wrap32(offsetX*36)),sourceY,sourceZ + binary32(wrap32(offsetZ*36))). A noncentral cell requires the returned effect and adds ModifyAnimation type 10, scales 0.7, anchor 34, loop true, destroy false, alpha 255, with other fields zero. It creates entity kind 0, adds Position at the captured effect location with y+5, zero offsets and null parent, then Collision radius 18 with zero offsets/visited. After those component notifications it reads the source Damage value and attribute, adds Damage with the supplied owner, then Garbage lifetime 2. Thus callback changes before the Damage reads are visible, while the captured position is retained. The center creates no extra damage entity.

After each cell, the captured BulletData record flags mask 1 is read afresh: if set, the effect must exist and receives raw Color arguments (255,255,255,3192). A null central effect is allowed only when that flag is clear. Finally, the captured record category (+0x20) is read: category 1 removes any current ModifyAnimation (notification before pool return) and adds type 5, angle 180, maxFrame 20, unit scales, destroy true, loop false, alpha 255, all remaining fields zero. Other categories add Garbage lifetime 1 to the source. No RNG is consumed. Failure preserves earlier effects/components and skips subsequent cleanup; ordinary C++ ownership replaces managed enumerator disposal.

### Collision candidate traversal and deferred delivery

CollisionSystem.Init (0x1145e68) builds And({32,0}): Collision and Position. The second int32 array element is zero-initialized; only element 0 is explicitly written to 32. NeedsUpdate (0x1145f38) returns enabled (+0x18), ignoring pass. Update (0x1145f40, 2628 bytes) first enumerates this live subset and resets each required Collision.visited byte (+0x20) to false. After disposal it opens a fresh outer cursor. For each outer entity it sets visited true, then opens another fresh cursor over the same subset. Each inner entity and Collision are required before the self comparison; self and already-visited inner entities are skipped. With a stable subset this considers each unordered pair once, in subset discovery order.

The following exclusions run in order: Human/Human, Enemy/Enemy, Bullet/Bullet, Bullet/Human, Human/Bullet, Effect/Human, Human/Effect. Slots are Human 14, Enemy 24, Bullet 29, Effect 26. Multiple tags retain all exclusions. For each surviving pair, first then second, presence of Parameter slot 23 requires parameter key 0; Parameter.value is wrap32(raw value + extra), and signed values below 1 skip the pair. Missing Parameter is allowed, whereas null/missing key 0 faults. There is no destroyed-entity guard or other owner/faction test here.

After these gates, the inlined geometry matches the ported CheckHit formula: binary32 position plus signed int32 offsets, squared 3D distance, and inclusive comparison against the signed int32 wrapping square of the radius sum. NaN distance is rejected. Both Collision components are required at this stage. Hits append the ordered entity pair to the system's persistent list at +0x28. Only after all inner/outer cursors are disposed does Update send World event 29 for each queued pair, with no geometry, HP, destroyed or component recheck. Contact callbacks can therefore invalidate later pairs; downstream handlers retain responsibility for their own guards. A projectile hitting two enemies can produce two queued events, but OnBulletHit removes Projectile/Collision on the first, causing its second invocation to return without damage.

The list is cleared only after successful delivery of every event. There is no clear at entry: detection or subscriber exceptions leave prior queued pairs in place, and a subsequent update appends and then delivers them again. The port retains this observable behavior and checks queue mutation during delivery using a version counter. It uses standard C++ vector storage; public collection implementation details are not reconstructed. Live subset ordering/version checks and managed exception identity remain outside the port.

Desktop binding: MissionScene owns the initialized persistent pass, uses the existing live subset cursor and forwards event29 to native Human/Enemy receivers after Move11. Duplicates can consume more than five points from the same Parameter in one update, because the limit applies to each queue entry. A negative buffer becomes zero without adding EXP and the entry is removed. Earlier writes/removals survive a later null/missing-data failure. No human/enemy/alive/destroyed predicate is consulted.

Parameter.AddLevel (0x1178e2c) returns 0 without a write if oldLevel>=maxLevel, even for a negative amount. It does not recalculate any combat value.

### Human contact reaction

`HumanSystem.OnCollide` (game:0x06000ed0, 0x1157be0, 708 bytes) selects the first Human-bearing entity, otherwise the second. The first entity is required. It then rejects Damage slot 33 on either input (first short-circuits the second), a null/destroyed selected Human, and Human states 4 or 5. Only then does it select the first Enemy-bearing entity, otherwise the second; no Enemy returns. It requires EnemyData and returns when its flags include mask 1. It does not inspect HP, invincibility, enemy destroyed state, Cell, Projectile or Bullet presence; no damage is applied by this receiver.

Displacement is binary32 +10 when EnemyComponent.flags +0x14 includes mask 1. Otherwise it requires the human's character record and uses +3, except a sub-character (record flags mask 4) whose Z is strictly greater than the hero's Z uses +0.5. Equality and unordered/NaN comparison use +3. Human Z is captured before MemberSystem.hero is resolved; the current human Position is fetched again for the store afterward. The component flag and record flag are different fields: record flag 1 skips the whole reaction; component flag 1 selects +10 and bypasses the character/hero lookup.

Side effects, in order:

1. Add displacement to live Position.z, then assign Speed.z to displacement; x/y velocity stay unchanged.
2. Call CutInAnimation(entity,4,36).
3. Require Direction and set locked=true; this is not conditional on Direction presence.
4. Read live Position x/y/z and create effect (0,2,0) at (x,y+10,z-12).
5. Invoke the ported HumanSystem.ChangeState(entity,3), including its live pre/post hooks and frame reset.

Callbacks can replace Position or change the state seen by ChangeState. Late failures preserve earlier stores: a missing Direction faults after movement and CutInAnimation; an effect failure prevents the state change. There is no rollback or post-callback destroyed guard.

Port: `human_contact.hpp/.cpp` calls the existing state-transition module and leaves hero lookup, cut-in animation, effect creation and live destroyed state as explicit host services. Contract tests cover both input orders, all displacement choices, NaN/equality, Damage/dead/data guards, missing components, position replacement, captured-vs-live position reads, state callback changes and partial failure. The entity-event adapter now delivers this receiver before EnemySystem.OnCollide, with an integration test covering both real bodies; the integration now starts at the enabled-gated CollisionPass over a live entity group; complete world wiring remains open.
