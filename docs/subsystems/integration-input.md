# Mission input and camera integration

The S1 mission hosts share native movement/attack handlers, map/camera/cell visibility and ordered replay. The desktop pointer adapter supplies the selected QuestForm map registration and rectangle-hit contracts; native Surface touch queues and multi-touch remain unbound. Host entry and the authoritative stub table are in [integration](integration.md).

## Overview

`MissionProfile` owns replay and map capture; `MissionWindow` converts physical desktop events into the same profile calls. `MissionHumans` retains Input0/Stage listeners, while `MissionSpatial` owns map, camera, cursor and visibility state. The shared host executes native game bodies through the scheduler rather than mutating actor positions from physical events. Static game contracts are detailed in [UI](ui.md#quest-camera-cursor-and-viewport) and [ECS](ecs.md).

## Behaviour

### Map pointer registration and capture

QuestForm.Draw calls `CheckFirstTouch(17)`: without a match it registers the current VIEW rectangle; with a match it registers `(-1000,-1000,2000,2000)`, with Drag binary32 factors `(1,1)` in either case and flags40 for the captured case. Group/value is17/0. The group-only CheckFirstTouch checks the down component at Surface+0x40 (group at component+0x18), then searches Surface+0x20's start list; this is evidence for the selected capture query, not a port of those lists. `TouchOption.Drag` stores factors at+0x18/+0x1c and clears flags when its boolean option is false; the explicit Flag call writes40 at+0x10. Confidence high; bounded exports are listed below.

`quest_map_touch_region` expresses that selected registration, and `input_hit_rectangle` ports SurfaceBase.CheckHitPointRect with inclusive left/top and exclusive right/bottom edges. Right/bottom sums wrap as signed int32; no widening, saturating bounds or positive-size rule is substituted. The desktop initial VIEW is `(0,0,drawable_width,drawable_height)`. The captured rectangle is finite: its right/bottom edges are1000, independent of viewport size. Native DoEvent also rejects component-rectangle misses before options or retained-point lookup, including active drag/pinch. TOP_PRIORITY8 and CANCEL_SCREEN_LIMIT32 compose flag40; they do not bypass that gate. A viewport wider than1000 can therefore admit a down at x1200, while the selected captured region rejects a later motion there. The desktop test preserves this finite-region result; full native component refresh/cancellation timing remains unbound.

`MissionProfile::map_pointer_touch(type,x,y,dx,dy,pinch_delta)` requires `mission_presentation`, map and native input. Coordinates and deltas are signed int32 drawable pixels. Type0 acquires capture only after a hit; type8 requires capture and a hit in the captured rectangle. Type1 requires existing capture and releases regardless of coordinates. Type12 requires a hit in the current region, sends the native pinch followed by type1 to clear pinching, and preserves any right-drag capture. Rejected actions do not enter QuestForm.OnTouchEvent. Accepted actions retain its event9-before-group17 ordering; pinch subsequently emits event25. Reports expose `map_pointer` capture, accepted/rejected/cancellation counts, last coordinates, current rectangle and flags.

Physical right-button down/motion/up map to types0/8/1. SDL window coordinates and relative motion convert to drawable pixels; motion retains fractional remainders. A wheel unit supplies20 raw pinch units, followed by immediate native release. This is explicit desktop mapping policy. Focus loss cancels capture and clears pending physical deltas; entering a retained talk/stage modal or held return also cancels through the desktop adapter. Cancellation sends release for an active capture and is otherwise inert. It does not reconstruct native Surface release/cancel queues. The existing pinned SDL3.4.18 dependency (zlib license) supplies ordinary mouse events and [automatic capture during a pressed button](https://wiki.libsdl.org/SDL3/SDL_CaptureMouse); its queue/capture implementation is reused, not reconstructed.

Replay `step pointer type x y dx dy pinchDelta` accepts types0/1/8/12 with signed int32 fields; `step pointer cancel` releases capture. Both require native presentation/map/input. Steps use the same ordered positive form-frame time as other replay actions. `step camera type dx dy pinchDelta` remains the separate normalized diagnostic entry and bypasses pointer hit/capture selection; its types0/1/5/8/12 retain their handler contract. Group17 does not generate Cursor events2/4: GameView's dispatcher returns for that group and its camera override is inert. Neither the pointer adapter nor normalized camera replay invents a cursor producer.

### Replay state coverage (S1 A5)

Complete reached-world hashing remains open. Existing JSON reports are observations: they omit future-determining state and some helpers query/create subsets or invoke drawing observers. Hashing requires const, side-effect-free owner snapshots. Entity snapshots must include stable host handles (temporary native ID-1 can repeat), component/reference/shared-array identities, registry/subset physical slots/free lists and ID counters. Human/Stage/Results need full RNG seed array/indices, roster/formation, quotas, lottery scratch, input/pulses, grant cursors, modal answers and deferred return. Scene/Spatial/Events/Profile also retain animation clocks, collision/emitter/destruction/EXP queues, Info bars, camera/cell/visibility order, event/modal/reveal state, replay position and enabled/paused state. Numeric widths and exact binary32 bits, null/length/schema markers and immutable-input fingerprints must be canonical; raw pointers/padding, nondeterministic clocks and GPU handles are excluded. Sorting native IDs or hashing only current report fields cannot establish A5. Existing ported gameplay bindings take priority over this additional diagnostic infrastructure.
